## 1.5 从图上取到的具体设计事实（可直接照做，不需再猜）

### 时间线

- 工具条右侧顺序固定为：`显示全部` → `共 N 条排期` → `日 周 月 年` → `定位今天`；
  选中的尺度是**深色实底**，未选中是描边/文字。
- 刻度是**两行**：上行居中「2026」（年），下行月份名；「月」尺度下**10 个刻度**（三月～十二月）。
- 行是**斑马纹**（偶数行整行浅底），条是**实心灰块**贴在行内左侧，订单名跟在其右。
- **今天**是一条贯穿全行的竖直虚线 + 顶部黑色胶囊「今天」，不是单元格高亮。
- 底部有横向滚动条：**内容超宽时横向滚动，不压缩日期间距**。

### 日历

- 左池标题带计数「未排期订单池 (1)」，下面是 `筛选` 下拉；卡片四行：订单名 / 彩色标签 / 客户·来源 / 金额。
- 日历头：`‹ ›` + `today` + 居中「2026年7月」+ 右侧 `month|week` 分段（选中深色实底）。
- 日期数字在格子**左上角**；今天用**黑色实心圆 + 白字**。
- 订单条**跨格连续**、圆角、文字左对齐在条内，**按来源着色**；同日多条**纵向堆叠**；
  跨周时**截断后续画**。
- 周首为「周日」。

### 看板

- 列头：状态圆点 + 阶段名 + `数量 ¥金额合计`；列与列之间有竖向浅分隔线、浅底。
- 卡片：订单名 → 客户名（无客户显示"未分配"）→ 金额（右对齐）→ 日期（左下）；逾期有红色角标。
- 底部说明原文 **「看板拖拽切阶段」**——即拖拽是**真实业务写入**，不是纯视图。

### 列表（与现状差异最大）

- 顶部页签：`列表` / `已归档`；右侧 `+ 视图` / `导出订单` / `导出文件夹`。
- 筛选行：阶段 / 来源 / 状态 / 结束日期区间 / 搜索。
- 表格 11 列：`☐  ID  客户  项目名称  来源  类别  阶段  DDL  收入  实收  收款  排期`。
- 现有实现是**卡片式行**（`order-code` + `order-row-title` + `order-row-meta`），无 `<table>`。

### 客户

- 表格：`☐  ID  客户名称  平台(链接)  偏好  标签  累计消费  购买次数  备注  操作`。
- 标签是「VIP / 新客户 / 回头客」三种徽章；结合累计消费看，**像按消费额自动分层**。

### 画廊

- 筛选：阶段 / 来源 / 客户 / 类别（四个下拉）。
- 4 列瀑布流，保留原始宽高比，图片垂直紧密堆叠，**截图中无文字图注**。

## 4. 拖拽排期：可行性与安全风险

### 4.1 可行性

技术路径现成：HTML5 `pointer` 事件（不用原生 drag，避免与未来 Finder 拖入冲突）+
`update_order_details(expectedRevision)`。日历格子只负责命中测试，写入仍走同一条命令。

**必须先答的语义问题**（见 §9）：单日放置写哪一端、区间订单是平移还是改端点。

### 4.2 六个必须防住的风险

| 风险 | 说明 | 处理 |
|---|---|---|
| 静默保存 | 松手瞬间就写库 | **强制二次确认**：松手只生成"拟修改"预览，确认才 `invoke` |
| revision 冲突 | 拖拽期间详情页可能改过资料 | 用 `expectedRevision`，冲突时展示"订单已变化，已刷新，请重新拖" |
| 误触终态 | 拖已完成/已取消的单 | 终态订单**禁止拖拽**，只允许在详情里改资料 |
| 混淆开工/完成 | 拖到今天就自动开工 | 日历**只写计划日期**，绝不改 `started_at/status` |
| 队列被改 | 拖拽顺带调整排队 | 队列只由 `queue_move` 改，日历不碰 |
| 与 Finder 拖入冲突 | 未来 DEV-07-FINISH 要开 Tauri drag-drop | 日历用 pointer 实现，不依赖 HTML5 DnD，两者可共存 |

### 4.3 键盘可达

拖拽必须有等价键盘路径：在未排期池里选中订单 → `Enter` 打开"安排到…"输入日期 →
确认。否则只有鼠标能用。

## 5. 画廊资源管理与隐藏机制

### 5.1 核心矛盾

`attachments` 现在**不区分**"客户给的参考图"和"我画的成品"。直接全量进画廊，
等于把别人的图当成自己的作品展示——这是产品风险，不是技术细节。

### 5.2 两个方案

| | A：`attachments` 加两列（推荐） | B：独立 `gallery_items` 表 |
|---|---|---|
| 迁移 | `ALTER TABLE` 两列 + 回填默认值 | 新表 + 外键 |
| 标记 | 附件面板里一个"设为作品"开关 | 同样要入口，但数据在另一张表 |
| 删除订单 | 附件行级联消失 → 画廊条目自动消失 | **必须额外删表行**，否则残留指向已删附件 |
| 隐藏 | `gallery_visible = 0` | 同表一列 |
| 复杂度 | 低 | 中 |

**推荐 A**，理由：`attachments` 已是文件元数据的唯一真源，再开一张表会制造"两处都能改可见性"的分叉；
且 A 让 DEV-07-PRE 的删除设计**不需要追加清理逻辑**。

### 5.3 隐藏语义

- 隐藏 = 只从默认网格消失，**文件不动、附件仍归属订单**；
- "已隐藏"是一个独立筛选页签，可恢复；
- 删除订单时，隐藏与否不影响文件生命周期——都跟着订单走。

### 5.4 "展示"不等于"发布"

Core 是离线应用。本轮"展示"只表示**本机画廊可见**。
真正上传到 ArtFlow Desk Web 属于跨产品功能，需要独立的网络层、鉴权与发布流程，**不在本轮**。

### 7.2 880px 下限带来的硬约束（实测推算）

| 场景 | 可用内容宽 | 后果 |
|---|---|---|
| 880 窗口，侧栏展开 | 约 580px | 月历 7 列 → **每格 82px**，一天最多放 2 条 |
| 880 窗口，侧栏折叠 | 约 744px | 月历每格 106px，可放 3 条 |
| 看板 5 列 | 580px | 每列 116px，**卡片挤**；建议列最小 180px + 横向滚动，可见 3 列 |
| 画廊瀑布流 | 580px | 2 列（每列 280），1400 下 4–5 列 |
| 时间线"日"尺度 | 580px / 30 天 | 19px/天，1 天的条只有 19px 宽——需要最小条宽 + 端点标记 |
| 时间线"月"尺度（图一）| 580px / 10 个月 | 58px/月，单月条 58px 可读；与图一的 10 刻度一致 |
| 时间线"年"尺度 | 580px / 365 天 | 1.6px/天，条会退化成细线 → 年尺度应改为**按月分段**而不是按天 |
| 列表改 11 列表格 | 580px | **放不下**。图三那套列宽合计远超 1180px，880px 下只能横向滚动或裁列 |

导航从 7 项增到 9 项：矮窗口下已有 `nav { overflow-y: auto }`（1400×400 实测 189/324），
新增两项后这个滚动会更早触发，**不需要改布局**，但要在 DEV-06D-1 的几何检查里加一条
"9 项 + 400px 高仍能滚到折叠按钮"。

## 8. 分期开发计划

| 阶段 | 目标 | 依赖 | 必须通过 |
|---|---|---|---|
| **DEV-06D-1** | 一次 v4 迁移 + 看板视图（含拖拽切阶段）+ 客户标签/统计/跳转 | 无 | 迁移往返、看板与列表数据一致、筛选不丢、拖拽切阶段有确认且 revision 冲突可回退 |
| **DEV-06D-2** | 工作台多尺度时间线（只读） | D-1（若复用 v4 无强依赖） | 四种尺度的刻度正确、今天定位、900px 可读、无写入 |
| **DEV-06D-3** | 日历 + 拖放 + 二次确认 | D-1、D-2 | 拖放零静默写入、取消无副作用、revision 冲突提示、键盘等价路径 |
| **DEV-06D-4** | 画廊 + 标记 + 隐藏 | D-1、DEV-07-PRE 的设计已更新 | 未标记的图不进画廊、隐藏可恢复、查看器复用、缺图降级 |
| DEV-07-PRE | QA 限定永久删除 | D-4（删除范围要含画廊字段） | 沿用原 15 条 + 新增 2 条 |
| DEV-07 | 备份恢复 | D-1 的 v4 schema | 备份含画廊标记与标签 |

顺序理由：**先做唯一一次迁移**，把 schema 风险集中在一个阶段；只读视图（时间线）先于写入视图（日历）；
看板若允许拖拽切阶段，它就是第一个写业务数据的视图——因此它的确认与回退逻辑必须在 D-1 内做完，不能拖到 D-3。
画廊必须在永久删除之前落地，否则删除设计要返工。
