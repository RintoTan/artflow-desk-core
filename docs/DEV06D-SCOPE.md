## 3. 产品明确要求 vs 开发者推断（严格分列）

### 3.1 明确要求（来自本轮任务书）

1. 时间线只读，**不做拖拽改期**；
2. 时间位置**不等于**作品完成度；
3. 未排期订单**不得**自动生成计划日期；
4. 日历拖放**必须先确认**，取消时零写入；
5. 日历是"计划日期的另一个入口"，**不是第二套排期数据**；
6. 看板与列表**同一数据源**，切换视图不改队列、不改阶段、不丢筛选；
7. 客户下单次数**优先动态统计**，不建易失同步的冗余计数；
8. 画廊**不得**自动收进所有附件（参考图不等于成品）；
9. "展示"只表示**本机可见**，不得冒充已发布到互联网；
10. 新增导航图标沿用 Arctic Line 规范，不改已验收的七个；
11. 需要 schema 变更时走正规迁移，不重建正式库。

## 6. 推荐数据模型与 UI 结构（摘要）

### 6.1 schema（一次迁移 v3 → v4，四项一起做）

```sql
ALTER TABLE attachments ADD COLUMN role TEXT;             -- NULL / 'reference' / 'final'
ALTER TABLE attachments ADD COLUMN gallery_visible INTEGER NOT NULL DEFAULT 0;
CREATE TABLE client_tags (id TEXT PRIMARY KEY, name TEXT NOT NULL UNIQUE, created_at TEXT NOT NULL);
CREATE TABLE client_tag_link (
  client_id TEXT NOT NULL REFERENCES clients(id) ON DELETE CASCADE,
  tag_id    TEXT NOT NULL REFERENCES client_tags(id) ON DELETE CASCADE,
  PRIMARY KEY (client_id, tag_id)
);
```

理由：一次迁移比四次安全（正式库只经历一次结构变化）；`client_tag_link` 用 CASCADE，
客户删除时标签关联自动清理（客户删除本身仍未纳入范围）。

### 6.2 不新增的东西

- 不加"归档"状态：时间线/日历的"历史"用现有 `status` 过滤即可；
- 不建排期副本表：日历直接写 `orders` 的计划日期；
- 不建画廊专用文件目录：仍用 `attachments` 的原图与缩略图。

### 6.3 UI 信息架构

```text
侧栏（9 项，Arctic Line 新增 2 个）
  工作台    → KPI 卡片 + [项目时间线] + 提醒说明
  订单      → [列表 ⇄ 看板] 同一路由，视图状态存 localStorage
  日历      → 未排期池 + 月/周
  客户      → 列表 + 详情（标签、关联订单、最近下单）
  画廊      → 瀑布流 + 展示/隐藏切换
  流程模板 / 历史统计 / 设置 / 数据环境（不变）
```

## 8. 对 DEV-07-PRE 的影响（必须写进删除设计）

1. 若画廊采用 `attachments.role/gallery_visible`（推荐），**删除订单时随附件级联消失**，
   删除设计不需要新增表；但 `cleanup_tasks` 只处理文件，不处理"画廊索引"（本来也没有独立索引）。
2. 若采用独立 `gallery_items` 表，则删除订单必须同时清理该表，且要**先登记再级联**，
   否则残留行会指向已删附件。
3. 无论哪种，**隐藏状态不改变文件生命周期**：隐藏 ≠ 删除，删除订单仍然清文件。
4. `DEV07-PRE-DESIGN.md` 的 15 条测试矩阵需追加两条：画廊标记随订单消失、隐藏作品不被误删。
