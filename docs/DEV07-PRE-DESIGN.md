# DEV-07-PRE 设计审查：订单永久删除

- 日期：2026-11-17
- 性质：**开发前设计**，本轮不实现、不加 UI、不改数据库、不执行迁移
- 依据：D-00-27 / D-00-29 / FIX-05 摘要（非原文）+ 现有 schema 与领域代码
- 结论：**可以在不新增表、不改 schema 的前提下安全实现**；复用 `cleanup_tasks` + `run_cleanup`，
  不建第二套清理系统。需要产品裁定 6 项（§B8）

---

## B1. 目标与复用边界

**目标**：把一张被明确指定的订单连同它的专属数据彻底删除，且**不误删**客户、模板、
被其它订单引用的文件、编号高水位。

**已验证可复用的现成机制**（不是新造）：

| 机制 | 位置 | 用法 |
|---|---|---|
| 事务 | `environment::open_db` 的 WAL 连接 | 删除 + 登记清理任务同一事务 |
| 乐观并发 | `orders.revision` | `WHERE id=? AND revision=?` |
| 清理任务队列 | `cleanup_tasks`（含 `order_id`、`generation`、`attempts`、`state`） | 登记待删文件 |
| 清理执行器 | `domain/attachments::run_cleanup` | 代际守卫、受管路径校验、符号链接拒绝、引用检查、状态机 |
| 启动补偿 | `lib.rs:87` 启动时跑 `run_cleanup` | 崩溃后自动续做 |
| 幂等钩子 | `orders.request_id UNIQUE` | 建单已在用；删除可复用同思路（见 B3.6） |

**不新增**：表、列、迁移、第二套文件删除逻辑。

## B2. 删除对象与关系（按实际 schema）

### B2.1 依赖图

```text
clients ──(orders.client_id, ON DELETE SET NULL)──▶ orders      ← 删订单不影响客户
stage_templates ◀── orders.stage_template_id（普通 TEXT，无外键）  ← 模板完全不受影响
                                                        │
                          ┌─────────────────────────────┼─────────────────────────────┐
                          ▼                             ▼                             ▼
               order_stages (CASCADE)        order_events (CASCADE)        attachments (CASCADE)
               订单的阶段副本                 生命周期事件                   附件元数据（文件另算）
                                                                                  │
                                          cleanup_tasks.order_id（弱引用，无 FK）
                                          attachment_jobs.attachment_id（弱引用，无 FK）
```

### B2.2 逐问回答

1. **一张订单关联哪些表？** `order_stages`、`order_events`、`attachments` 三张表通过
   `order_id ... ON DELETE CASCADE` 强关联；`cleanup_tasks.order_id` 与
   `attachment_jobs.attachment_id` 是弱引用（无 FK）。
2. **哪些是订单专属？** 上述三张表里 `order_id` 等于该单的行，以及它们在代际目录下的
   原图/缩略图文件。
3. **事件删除如何影响统计？** 统计是**实时聚合**（`domain/stats.rs` 直接查 `orders` 与
   `order_events`），所以删除后该单的 created/completed/cancelled 计数与金额**直接从历史月份消失**。
   这是产品语义问题，见 §B4。
4. **阶段是否随订单删除？** 是。`order_stages.order_id` 是 `ON DELETE CASCADE`，
   且 `orders(id, current_stage_id)` 对它是可延迟外键，整个删除在事务提交时自洽。
5. **附件与原图/缩略图关系？** `attachments` 行随订单级联删除；**文件不会自动消失**——
   `rel_path` 是相对代际目录的路径，缩略图在 `thumb_rel_path`。必须在删除前把两个路径都登记进
   `cleanup_tasks`。
6. **客户与模板是否保留？** 客户：`orders.client_id` 是 `SET NULL`，删订单只把该单指过去的关系断开；
   **客户行本身不动**。模板：`stage_template_id` 没有外键，模板与它的步骤完全不受影响。
7. **编号与高水位是否变化？** 不变。高水位在 `state/highwater.sqlite`，与业务库分离，
   删除路径**不得触碰**它。
8. **能否用原编号再建单？** 不能。编号由高水位单调发号，删除不回退、不复用；
   `orders.code UNIQUE` 只在行存在时约束，真正的保障是"高水位永不回退"。

### B2.3 事务边界

```text
BEGIN
  ├─ SELECT code, revision, status FROM orders WHERE id = ?            -- 存在性与编号校验
  ├─ SELECT rel_path, thumb_rel_path FROM attachments WHERE order_id = ?
  ├─ UPDATE attachment_jobs SET state='failed', note='order deleted'
  │     WHERE attachment_id IN (SELECT id FROM attachments WHERE order_id = ?)
  ├─ INSERT INTO cleanup_tasks (generation, order_id, rel_path, reason='order_deleted')
  │     × 每个 rel_path / thumb_rel_path
  └─ DELETE FROM orders WHERE id = ? AND revision = ?
COMMIT
   ↓（提交之后，独立于事务）
run_cleanup(conn, layout, active_generation)
```

**为什么清理任务必须在 DELETE 之前登记**：`attachments` 行会随订单级联消失，
提交之后就拿不到 `rel_path` 了。

**为什么提交后才跑 run_cleanup**：文件删除不可回滚；放在事务里会让"数据库已删、文件删一半"
变得更难解释。登记在事务内、执行在事务外，失败留 pending 下次重试——这是现有的附件删除已经采用的模式。

## B3. 删除流程（逐步：成功 / 失败 / 可重试）

| # | 步骤 | 成功 | 失败 | 可重试 |
|---|---|---|---|---|
| 1 | 用户在该订单详情选择「永久删除」 | 打开确认对话框 | — | — |
| 2 | 显示不可恢复警告（列出将删除的内容与数量） | 用户继续 | 用户取消 → 无副作用 | — |
| 3 | 输入完整订单编号（`AF-YYYY-NNNN`） | 输入与目标一致才启用按钮 | 不一致 → 按钮禁用，不发请求 | 可反复输入 |
| 4 | 前端提交 `delete_order_permanently { orderId, code, expectedRevision, requestId }` | 进入后端 | 网络/桥接失败 → 提示重试，**不改本地状态** | 是 |
| 5 | 后端校验：存在 / `code` 匹配 / `revision` 匹配 | 继续 | `NOT_FOUND` / `CONFLICT` / `INVALID`，**不做任何写入** | `CONFLICT` → 刷新后重试 |
| 6 | 事务：登记清理任务 + 标失败待处理作业 + 级联删除 | 提交 | 任何一步出错 → 整体回滚 | 是（事务回滚后状态不变） |
| 7 | 提交后执行 `run_cleanup` | 返回 `{removed, alreadyGone, refused, failed}` | 部分文件删不掉 → 任务留 `failed`，**订单已删除**（两件事分开报） | 下次启动或下次清理自动重试 |
| 8 | 前端刷新：列表、统计、详情清空 | 列表少一条、当前选中清空 | 刷新失败 → 显示"已删除，请手动刷新" | 是 |

### B3.6 幂等

- 重复提交同一 `orderId`：第二次返回 `NOT_FOUND`。UI 文案为
  **「该订单已不存在（可能已删除）」**，不是"删除成功"——不假装第二次也成功了。
- 若产品要求"同一请求重放也返回成功"，需要一张删除留痕表（新 schema），
  本轮**不提议**；`request_id` 目前只用于建单幂等，删除沿用"明确失败"语义更安全。

### B3.7 UI 必须区分两件事

```
订单已永久删除。
附件文件清理：已删除 3 个 / 1 个暂时失败（重启后自动重试）。
```

**不能**因为数据库删成功就提示"全部清理完成"，也不能因为文件没删掉就说"删除失败"。

## B4. 统计与生命周期语义（需要产品确认）

删除订单后，所有统计都是**实时重算**，因此：

| 指标 | 变化 |
|---|---|
| 新建次数 | 该单创建月 −1 |
| 完成事件次数 | 该单的 `completed` 事件数从对应月消失 |
| 取消事件次数 | 同理 |
| 月度金额 | 该单 `amount_cents` 从创建月移除 |
| 当前订单数 | −1 |
| 「本月完成事件明细」 | 该单的行消失 |
| CSV 汇总 / 明细 | 下次导出即反映删除后状态 |

**这是产品语义，不是实现副作用**：历史统计代表"当前台账，按事件回溯"，而不是不可变审计流水。
如果产品希望"删除后历史月份的数字不变"，就必须引入不可变事件归档（新表 + 新语义），
与 `D-00-31` 的现有口径冲突——**本轮不建议**，列为待裁定（§B8 第 5 项）。

现有规则一律不动：完成按 `completed` 事件计数、金额按创建月归属、NULL ≠ 0、自然月与工作时区。

## B5. 文件清理安全

现有 `run_cleanup` 已覆盖大部分风险，删除路径只需**正确登记**，不要绕过它：

| 场景 | 现有行为 | 删除场景需补充 |
|---|---|---|
| 删除过程中程序退出 | 事务未提交 → 全回滚；已提交 → 任务留 pending，启动时续做 | 无（已具备） |
| 文件正在被查看 | macOS 上 `unlink` 成功，查看器仍显示已缓存图像直到刷新 | UI 删除后应关闭该单的图片查看器 |
| 文件不存在 | 标 `done`，计入 `already_gone` | 无 |
| 权限不足 | `remove_file` 失败 → `failed` + attempts+1 | 重试有上限吗？见 §B8 第 6 项 |
| 文件被多条记录引用 | 查 `attachments.rel_path/thumb_rel_path`，仍被引用则 `refused` | 级联删除后残留引用必属其它订单 → 正确拒绝 |
| 清理任务重复执行 | `state='pending'` 才处理，处理后置 `done`/`failed` | 无 |
| 删除后再次启动 | `lib.rs:87` 自动跑一次 | 无 |
| 恢复备份后旧任务 | `generation != active_generation` → `skipped_stale` | 无 |

**严禁**：用 `rel_path` 拼绝对路径后递归删除目录。现有 `abs_path()` + `is_managed_path()` +
`symlink_metadata().is_symlink()` 三重守卫必须继续走，不得为了"快一点"直接 `fs::remove_dir_all`。

**待处理作业**：`attachment_jobs` 有 `attachment_id` 无 `order_id`。删除前把该单附件的
`pending` 作业标为 `failed`（note=`order deleted`），否则下次启动会对着一张已不存在的附件做恢复尝试。

**quarantine 不参与删除**：隔离区只处理"文件存在但无引用"的孤儿，删除是"有引用且主动删"，
两者不要混。

## B6. 上线策略：两种方案

### 方案 A：先只在 QA 环境开放（推荐）

- **做法**：命令照常实现，但注册时按运行模式判断——生产构建返回
  `DENIED`（"此功能尚未开放"），QA 构建正常执行；UI 在正式环境隐藏入口。
- **成本**：约 30 行（一个环境判断 + 前端一个条件渲染 + 两条测试）。
- **风险**：低。正式用户完全碰不到；QA 数据可随便删、可重建。
- **代价**：不能交付给真实用户使用，DEV-07 的备份恢复没验收前也不该给。
- **与现有约束的一致性**：完全符合"不得在 DEV-07 之前引入不可逆删除"。

### 方案 B：直接在生产开放

- **前提**：必须同时具备"删除前自动备份"或"可回退"能力，否则一次误删无法挽回。
- **成本**：等价于先把 DEV-07 的备份做出来（ZIP 快照 + 校验 + 回滚），否则不成立。
- **风险**：高。当前没有备份，用户误删就是永久丢失 4 单里的任意一张。
- **结论**：不推荐在 DEV-07 之前采用。

**建议**：A。等 DEV-07 的备份/恢复/回退通过验收后，用一个独立的开关把它放开。

## B8. 待裁定（只列影响实现的）

| # | 问题 | 推荐 | 若不决定的后果 |
|---|---|---|---|
| 1 | 允许删除哪些状态的订单？ | 全部（活动/完成/取消） | 实现前必须定，否则命令签名要改 |
| 2 | 确认方式 | 输入**完整编号** + 二次按钮，不用勾选框 | 弱确认会让误删概率上升 |
| 3 | 删除前是否强制提醒备份 | 是（文案提醒 + 指向 DEV-07 前的"暂无备份"事实） | 用户可能以为有备份 |
| 4 | 何时在正式环境开放 | **方案 A：DEV-07 验收后再开** | 若选 B，必须先做备份，否则不可逆 |
| 5 | 删除后历史统计是否应保持 | 保持"实时重算"（现状） | 若要冻结历史，需新增归档表，属于新范围 |
| 6 | 清理失败如何呈现 | 分开报"订单已删 / 文件 N 个待重试"；重试次数上限建议 5 次后转 `failed` 并在环境页可查 | 无限重试会掩盖真实故障 |

**不在本轮范围**：客户删除、批量删除、回收站、自动归档。
