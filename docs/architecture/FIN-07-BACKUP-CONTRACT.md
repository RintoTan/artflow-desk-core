# FIN-07 冻结契约：财务数据的备份、恢复与跨版本回填

状态：**已冻结**（FIN-07 交付，`v0.1.2` 财务工作包 7/7）

上位文档：[DATA-SAFETY](DATA-SAFETY.md)、[BACKUP-COMPATIBILITY](BACKUP-COMPATIBILITY.md)、[DATA-LIFECYCLE](DATA-LIFECYCLE.md)

## 1. 范围

本批**不重新设计备份系统**，只把财务模块纳入已有保护：

| 做 | 不做 |
| --- | --- |
| 备份摘要增加财务四项计数 | 不新增 schema 迁移（仍为 v12） |
| 恢复期判定版本与财务结构是否自洽 | 不改备份格式（仍为 v1）、不改 `manifest.json` 结构 |
| 旧备份缺平台表时回填本机配置（规则 B） | 不改变财务业务规则、手续费算法、统计口径 |
| v12 四表逐字段往返验证 | 不做自动备份、云同步、加密、增量备份 |
| 恢复失败不切活动代际 | 不改原型 ZIP 拒绝政策、不降低 ZIP/SHA-256 校验 |

## 2. 摘要：只是数量

`DataSummary` 从数据库快照**临时计算**，不写入 `manifest.json`。

| 字段（JSON） | 来源 | 展示 |
| --- | --- | --- |
| `paymentPlatforms` | `payment_platforms` | 收款平台 N 个 |
| `paymentSchedules` | `payment_schedules` | 付款计划 N 项 |
| `paymentRecords` | `payment_records` | 收款流水 N 笔 |
| `refundRecords` | `refund_records` | 退款记录 N 笔 |

口径（这是库存清单，不是财务报表）：

1. 含已归档平台、已作废收款、已作废退款；
2. 回收站订单挂着的财务记录照样计入；
3. 不按订单状态过滤、不因取消而排除；
4. 不显示金额、客户姓名、联系方式、备注。

缺表处理：

- **表不存在** → 0（v9 及以前本来就没有财务表）；
- **表存在但统计失败** → 返回错误。不得用 `unwrap_or(0)` 把结构损坏伪装成零记录。

预览里的数字必须描述**这份包**，不得把本机待回填的平台数量混进备份原始数量。

## 3. 版本与结构判定矩阵

判定发生在**迁移之前**（迁移会把缺的表建出来，事后再判断就永远得到「有」）。

| 备份声明 | 平台 / 计划 / 收款 | 退款 | 结论 |
| --- | --- | --- | --- |
| v9 及以前 | 不该存在 | 不该存在 | 任一存在 → 拒绝 |
| v10 / v11 | 必须存在 | 不该存在 | 缺表或已带退款表 → 拒绝 |
| v12 | 必须存在 | 必须存在 | 缺表 → 拒绝 |

另外两条硬闸门：

1. `manifest.schemaVersion` 必须等于库内 `user_version`，否则拒绝；
2. 迁移完成后四张表 + v11/v12 的 12 条触发器必须齐全，缺一即拒绝切换。

## 3.1 已知限制：v10 带财务数据的备份不可升级

v11 的迁移以「三张财务表必须为空」为前提（`PRAGMA foreign_keys` 在事务内是 no-op，
三表互相引用时删父表会触发子表 `SET NULL` 并静默抹掉关联），因此：

| 备份 | 能否升级 |
| --- | --- |
| v10，三表为空 | 可以 |
| v10，三表有数据 | **不能**，v11 空表断言会让整次恢复失败 |
| v11 / v12，带数据 | 可以 |

**这个状态在应用内不可达**，证据（2026-11-25 复核）：

1. `711c70c`（v10）里对三张财务表只有三句 `CREATE TABLE` 与永久删除订单时的两条 `DELETE`，
   没有任何 `INSERT`，也没有任何命令或领域写入接口——v10 根本没有「录入计划/收款」的入口。
2. v10 的窗口只有一个提交（`711c70c` → `abeee2f`，FIN-01.1）。
3. 机内审计：数据根下不存在任何 v10 / v11 数据库（只有 v7 / v8 / v9 / v12）；
   全部 5 个备份包为 2×v2（原型血统）与 3×同一份 v7 快照，**没有 v10 或 v11 的包**。

**若真的遇到**（手改过的库、第三方构造）：恢复会在迁移阶段失败，不切 `active.json`、
不做部分导入、不产生虚构记录——安全，但提示来自迁移而不是预览。**预览阶段尚未提前判定这一点**，
列为已知缺口，见 §7。

## 4. 规则 B：平台配置回填

产品裁定（2026-11-25 冻结）：**恢复旧备份时保留当前平台配置，但仅限备份本身没有平台表的情况。**

| 场景 | 行为 |
| --- | --- |
| 包内没有 `payment_platforms`（v9 及以前） | 从**恢复前的活动代际**读平台，回填进隔离代际 |
| 包内有 `payment_platforms`（v10/v11/v12） | 严格按备份恢复，即使为空也保持空 |
| 包内声明 v10+ 却没有平台表 | 版本与结构不一致 → 拒绝 |

回填字段：

| 字段 | 处理 |
| --- | --- |
| `id` / `name` / `fee_rate_bp` / `archived` / `sort_position` / `created_at` | 原样 |
| `updated_at` | 记为本次恢复时刻 |

边界：

- 回填必须发生在隔离代际内，**不能**先写入当前活动数据库；
- 用普通 `INSERT`，不用 `INSERT OR IGNORE`：冲突就让整次恢复失败，不把配置冲突咽下去；
- 与「数据重置」的搬运语义不同：重置是维护动作，两个时间戳都原样；恢复是重建环境，
  `updated_at` 记为恢复时刻。两处各自实现，不合并成一个函数。

`payment_schedules` / `payment_records` / `refund_records` **任何版本都不回填**。
迁移前后比对这三张表的行数，数量变化即拒绝切换（防止迁移造假或丢数据）。

## 5. 失败保护

以下任一步失败：不切 `active.json`、不覆盖当前数据库、不删当前代际、不丢恢复前快照、
不把部分回填的库标记为成功；失败现场挪到 `recovery/` 供排查。

覆盖顺序：manifest/ZIP 校验 → 恢复前自动快照 → 隔离代际解包 → 完整性/外键 →
版本一致性 → 财务结构一致性 → 迁移 → 表与触发器齐全 → 平台回填 → 业务历史行数比对 →
附件引用 → 时区 → 摘要 → 高水位合并 → 原子切换。
