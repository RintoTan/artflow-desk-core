## 1. 看板拖拽 PARTIAL 的根因

### 1.1 代码事实（不是猜测）

`src/components/OrderBoard.tsx` 修复前：

```jsx
<article className="board-card" draggable={!busy}
         onDragStart={(e) => {
           e.dataTransfer.setData("text/minidesk-order", order.id);
           e.dataTransfer.effectAllowed = "move";
         }}>
  <button className="board-card-open" onClick={...}>…整个卡片内容…</button>
```

两个明确的 WebKit 不兼容点：

1. **整个卡片正面是一个 `<button>`**。WebKit 不会从表单控件（button/input）上发起 HTML5 拖拽，`dragstart` 根本不会冒泡到外层 `<article>`。Blink 允许，所以无头验证一直是绿的——这正是"按钮路径 PASS、拖拽 PARTIAL"的形态。
2. **`dataTransfer` 用了自定义 MIME `text/minidesk-order`**。WebKit 的 DataTransfer 只保证 `text/plain` / `text/uri-list`，自定义类型读回空串。

### 1.2 归类

| 分类 | 判定 |
|---|---|
| A 拖放事件没有触发 | **命中**（第 1 点） |
| B 事件触发但目标列命中失败 | 次要风险（第 2 点会导致 id 读不到） |
| C 业务规则拒绝 | 不是主因：按钮路径同一条规则是通过的 |
| D 确认框焦点 | 不是主因 |

### 1.3 修复（不改变业务规则）

- 卡片左上角新增**独立拖拽柄** `.board-card-grip`（`div`，不是 button，`role="button"` 但不参与 Tab 顺序），`draggable` 只挂在这个柄上。
- 数据改用 `text/plain` + `minidesk-order:` 前缀；同时保留 `dragging` 状态兜底，读不到也认得出。
- 目标列补 `onDragEnter` 高亮，`dragover` 保留 `preventDefault`。

**限制说明**：以上是代码层证据 + WKWebView 已知行为，**未在 WKWebView 实机复验**，需 QA-02 确认。

## 2. 看板 A/B 方案

约束：最小窗口 880px，`.main` 可用宽度约 570px；列宽下限 190px（再窄读不了标题）。

### 方案 A：传统 Kanban 优化版

保留全部阶段横向排列，加阶段导航、模板筛选、非法目标禁用态。

| 维度 | 评估 |
|---|---|
| 900px 阅读效率 | 差：570px 只放得下 2 列，5 个阶段要横向滚 3 次 |
| 1400px 空间利用 | 好：5 列刚好铺满 |
| 多模板兼容 | 中：同名阶段合并成一列，目标解析仍要回落单 |
| 拖放可靠性 | 中：目标常在视野外，拖拽需要"边拖边滚" |
| 键盘可达 | 中：需要额外的横向移动键 |
| 学习成本 | 低（最熟悉的形态） |
| 与卡片视图差异 | 低：都是"一屏看很多单" |

### 方案 B：聚焦式阶段看板（采纳）

顶部保留**全部阶段**导航（含每列数量），主体只渲染当前阶段 + 相邻阶段（按实测宽度 1–3 列），`‹ ›` 步进。

| 维度 | 评估 |
|---|---|
| 900px 阅读效率 | 好：2 列 × 约 270px，标题可读 |
| 1400px 空间利用 | 好：3 列，列宽上限 300px 不拉伸 |
| 多模板兼容 | 好：拖放目标永远在视野内，且仍按目标订单自身模板解析 |
| 拖放可靠性 | 好：短距离拖动，目标列可见 |
| 键盘可达 | 好：导航胶囊 + `→ 下一阶段` 按钮 |
| 学习成本 | 中：需要理解"一次看一段" |
| 与卡片视图差异 | 高：卡片=逐单精读，看板=按阶段推进 |

### 结论

选 **B**。理由不是"避免滚动"，而是：**在 570px 里，A 的目标阶段必然在视野外，拖拽只能靠"边拖边滚"，这与"拖放要可靠"直接冲突**。B 让合法目标始终可见，且不改变任何业务语义。

**涉及产品规则的部分（不自作主张）**：同名阶段仍按名称合并成一列（展示层），拖动时回落目标订单自身模板解析 ID；跨模板不可互换。若产品希望"看板按模板分组"，那是新的产品规则，本轮不做。

## 3. 表格 A/B 方案

### 方案 A：优化传统表格

固定编号列、压缩列宽、次要列折叠、局部横向滚动。

- 900px：仍需横向滚动（十列最小需求约 900px+），只是不再断字。
- 1400px：完整十列，密度高。

### 方案 B：自适应高密度列表（采纳）

- 容器 < 760px：压成**四列两行格**——`编号` / `委托(标题 + 客户·来源)` / `阶段(+状态)` / `交付(+金额·风险)`。
- 容器 ≥ 760px：完整多列表格（含类型、排期）。

- 900px：四列全在一屏，无横向滚动，可纵向扫读。
- 1400px：十列真表格，保留数据密度优势。

### 结论

选 **B**。判据是实测：方案 A 在 900px 下仍需滚动（十列放不下），而用户明确不喜欢横向滚动；B 在同一宽度下把"必须知道的五项"放进一屏。

## 4. 页头工具区

两级：

- **一级**：标题 + 数量 · 三视图切换 · 新建（主按钮）。
- **二级**：搜索 · 来源 · 状态胶囊 · 密度 · 导出（次级，靠右）。

要点：状态用胶囊而非下拉（生效条件一眼可见）；`head-spacer` 把辅助操作推到右侧；页头仍是三视图共用的一份，切换时位置不变（几何断言保持）。

## 5. 抽屉关闭

原实现是 `position: sticky; float: right` 的浮动小按钮，压在内容上。

改为**抽屉标题栏** `.drawer-bar`：左侧「订单详情」，右侧 32×32 关闭按钮（`currentColor` 描边叉号，与 Arctic Line 同风格），`sticky top` 常驻，hover/focus 有状态，Esc 仍可用，脏草稿仍阻止静默关闭。

同时修掉一个真缺陷：**点"已选中的那张卡"以前什么都不发生**（`attemptSelect` 直接 return），导致抽屉打不开。

## 6. 底部安全距离

在四类滚动容器上给内容底部留白（≥20px，实测 22px）：`.order-rows` / `.board-cards` / `.table-wrap`，详情 34px。

不做：不加外层高度、不制造第二层滚动、不动 DEV-06B 的列表高度门禁。
