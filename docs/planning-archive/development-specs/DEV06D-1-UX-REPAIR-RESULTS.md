## 1. P0：`orders_view_mode` DENIED 的真实根因

### 1.1 根因

不是 QA/正式配置差异，也不是"可写不可读"，而是**一处漏登记**：

`src-tauri/src/commands/preferences.rs`：

```rust
const ALLOWED_KEYS: &[&str] = &[settings::KEY_LIST_DENSITY];
```

上一轮我在前端加了 `preference_get("orders_view_mode")`，但**没有把这个键加进白名单**。
于是读被拒（`不允许读取的偏好项`）、写也被拒（`不允许写入的偏好项`）。

### 1.2 为什么用户只看到"DENIED"而没看到别的

两处掩盖叠在一起：

1. 读取写在 `Promise.all` 里，一个键被拒 → 整个列表加载失败。
2. `changeView` 的 `catch {}` 把写入失败**静默吞掉**，界面上看不出"其实没记住"。

所以现象是：进订单页就报 DENIED，且视图选择永远不会被记住。

### 1.3 修复（三处，都在真实契约上）

| 位置 | 修复 |
|---|---|
| `store/settings.rs` | 新增 `KEY_ORDERS_VIEW_MODE = "orders_view_mode"` |
| `commands/preferences.rs` | 白名单加入该键；值域校验只接受 `cards/board/table` |
| `pages/OrdersPage.tsx` | 偏好读取改为 `readPreference()` 容错包装：读不到 → 返回 null → 回退卡片；**不再拖垮列表** |

写入失败不再静默：界面出现"当前视图已切换，但没能记住偏好（原因）"，`role="status"`。

**没有**做的事：没有放宽成"任意键都能读写"；没有吞掉 DENIED 假装成功；没有绕过偏好接口直接改库。

### 1.4 测试

| 层 | 用例 |
|---|---|
| Rust `tests/preferences.rs`（5） | 键在白名单内；未设置返回 `None` 而非空串；写读往返；新建连接仍读得到（模拟重启）；未知键不在白名单 |
| 前端 `OrdersPage.views.test.tsx`（5） | 未设置默认卡片；存过 `board` 进看板；非法值 `timeline` 安全回退；切换写入同一个键名；**读被拒时列表照常显示并提示没记住** |

## 2. 订单工作区：三视图不再是"堆在详情上方"

### 2.1 结构

| 视图 | 布局 |
|---|---|
| 卡片 | **完全保持原样**：左侧列表 + 右侧详情并排（窄容器下按既有容器查询规则上下排） |
| 看板 | 占满主工作区；点击卡片 → 右侧固定抽屉（`width: min(560px, 92vw)`）打开同一份详情 |
| 表格 | 同上；表格在自己的容器内横向滚动 |

关键实现选择：**详情只有一个实例**（同一段 JSX、同一份 state），只是按视图换定位类
（`.orders-detail` ↔ `.orders-detail-drawer`）。没有第二套订单编辑逻辑，也没有复制表单。

- 抽屉关闭：`关闭详情` 按钮 或 `Esc`。
- **有未保存草稿时不静默关闭**，提示"请先保存或撤销"——草稿留在内存里，不假装已关闭。
- 进入视图时**不自动弹抽屉**（第一版会，截图发现后修掉）。

### 2.2 卡片视图保护证据

`layout:check` 原有 24 项（含行高、可见行数、气泡、导航对齐、列表/详情不重叠）**全部保留并通过**，
阈值未改。卡片视图仍是默认视图（无偏好 / 非法偏好都回退卡片）。

### 2.3 统一头部

三种视图共用同一套头部结构：`标题 + 数量摘要`（左）、`视图切换 + 导出 + 新建`（右）；
筛选行统一为 `搜索 / 来源 / 状态` 三个等高控件，`.list-tools` 统一 `gap: 8px`，
窄窗换行而不挤压输入框。新建仍是主按钮，导出是次级。

## 3. 看板空阶段

**问题**：原来只渲染"有订单"的阶段列，一张单时没有可拖的下一阶段。

**修法**：列集合改为**可见活动订单各自模板里的全部阶段**的并集（按最小位置、再按名称排序）。

- 阶段全部来自真实模板，**不虚构**；
- 空列显示"拖到这里"，是合法放置目标；
- 落到某列时仍然回到**目标订单自己**的阶段表解析 ID：
  该订单没有这个阶段 → 拒绝；同名阶段不唯一 → 拒绝；
- 跨两个及以上阶段 → 拒绝；未开工返工 → 拒绝；终态 → 拒绝。

**键盘路径**：卡片下方新增 `→ 下一阶段名` 按钮（仅在该订单可推进时出现），
点开同一个确认框。Tab 可到、Enter 可触发。

跨模板顺序没有"正确答案"（两个模板的首阶段都是 0 号位），因此同序号按名称稳定排序，
文档里明确写了"顺序只求大致从左到右，不承诺业务含义"。

## 4. 确认框与焦点

删掉了自造的 `.board-confirm`，改用既有 `ConfirmDialog`：

| 要求 | 现状 |
|---|---|
| 打开后焦点进入 | 焦点落到「取消」（既有约定：危险操作不默认确认） |
| Tab 不逃出 | `ConfirmDialog` 自带焦点环 |
| Esc 取消 | 通过 `modalStack` 只在栈顶响应 |
| 取消后焦点返回 | 记录打开前元素并还原 |
| 确认只提交一次 | 内部 `inFlightRef` + `busy` |
| 请求期间防重复 | 同上 |
| revision 冲突 | 父组件刷新列表并提示"看板已刷新，请重新拖动" |
| 草稿不丢 | 走既有 `unsavedRegistry`，看板操作不碰订单资料草稿 |

行为测试：拖到下一阶段 → 弹框；取消/`Esc` → `onApply` 未被调用；确认 → 只调用一次且带目标阶段 ID。
