# 关键产品决策

每条都记录「决定了什么 / 为什么 / 代价」。

## 1. 本地优先，不做云同步

数据存本机 SQLite + 文件目录，不引入账号体系。
**代价**：多设备需要手动迁移（备份包）。**理由**：目标用户是个人画师，客户信息敏感，云端方案会带来合规与运维负担。

## 2. 单画师，不做多用户

没有角色、权限、协作。
**代价**：工作室多人无法共用一个库。**理由**：多用户会把复杂度推高一个量级，而目标用户并不需要。

## 3. 受控跳级，而不是任意改阶段

`skip_stage` 必须至少跨过一个中间阶段，且被跳过的阶段以快照写进事件。
**理由**：跳级是真实存在的工作方式（客户只要成图），但它不能伪装成「这些阶段都完成了」。历史必须能还原当时跳过了哪些阶段。

## 4. 计划日期与实际时间分离

`planned_start_date` / `planned_delivery_date` 是人为排期；实际发生的时间只来自事件（`work_started`、`completed`、`rescheduled` 等）。
**理由**：混在一起会导致「改期后历史被改写」，也会让统计失真。

## 5. 数据代际（generation）

每次 schema 升级或备份恢复都生成新代际目录，`state/active.json` 原子切换，旧代际保留。
**理由**：让「升级失败」和「恢复失败」都不会破坏当前数据；代价是磁盘占用增长。

## 6. 事件表保存阶段名称快照

事件里存 `from_stage_title` / `to_stage_title` 与跳级快照，而不是只存 id。
**理由**：模板改名或删除后，历史仍要读得懂。

## 7. 备份是整库快照，不是表级导出

用 `VACUUM INTO` 产出一致性快照，附件按目录整体打包，manifest 记录每个文件的 SHA-256。
**理由**：表级导出会漏掉未来新增的表；SQLite 在 WAL 模式下直接拷文件会丢已提交事务。
**代价**：包体积较大，未做增量。

## 8. 恢复只在隔离代际里进行

恢复前先给当前数据做一次完整备份；解包、迁移、校验都在新代际完成，全部通过才切换指针。
**理由**：恢复是最高风险操作，宁可多花磁盘也不能让「恢复失败」变成「数据没了」。

## 9. 资产协议按活动代际授权

`assetProtocol.scope` 为空，启动时只对当前代际的 `attachments` 目录 `allow_directory`。
**理由**：早期用 `generations/*/attachments/**` 的宽泛 glob，实测能读到别的代际的附件（含跨代际符号链接）。

## 10. 不自动清理任何文件

隔离文件、旧代际、作业记录都只做「盘点 + 用户确认后手动清理」，没有定时器。
**理由**：自动清理在单机应用里无法可靠判断「这个文件还有没有用」，误删的代价远高于磁盘占用。

## 11. 参考图不自动进入作品集

附件属于订单，不流向任何展示模块。
**理由**：画师的未公开稿件不应该因为「上传了参考图」而被自动公开。

## 12. 关于页承载数据环境信息

原来的「数据环境」独立入口合并进「关于软件」，只保留一个入口。
**理由**：两者都是「了解这个软件现在是什么状态」，分开只是让用户多点一次。

## 13. 放弃 macOS 交叉编译 Windows

试过在 macOS 上交叉编译 `x86_64-pc-windows-msvc`，卡在缺 `llvm-rc` / `llvm-lib`（资源编译器与归档器），补齐工具链的成本高于收益。
**改为**：GitHub Actions `windows-latest` 原生构建。
**代价**：每次构建要等 CI；本地无法出 Windows 包。

## 14. 不把「永久删除」当作备份的前提

早期设想是先把废弃订单彻底删掉再备份，以控制包体积。
**否决**：删除会破坏「历史不可改写」这条底线，也让误删无法通过备份找回。
**改为**：备份包含全部数据；体积问题交给用户自己判断（导出时可见总大小）。
v0.1.1 的备份同样不裁剪回收站（见 §18），这条决策继续有效。

## 15. 删除是可见性，不是业务状态

订单与客户的「删除」只写 `deleted_at` / `deleted_batch`，不新增 `trashed` 状态，也不改 `status`。
**理由**：`status` 是业务终态（进行中/已完成/已取消），如果混入「已删除」，会污染统计口径，还要再改一次 CHECK 枚举（v6/v7 已经为此整表重建过两次）。
**代价**：每个查询都要显式回答「要不要看回收站」，靠视图与 lint 强制。

## 16. 查询用途决定可见范围：视图 + 守卫 + lint

三层，各管一件事：读用 `*_visible` 视图；按 id 的读写用 `store::visibility` 守卫；新查询由 SQL lint 拦截（裸 `FROM orders` / `FROM clients` 即失败）。
**理由**：只靠「每个开发者记得加 WHERE」必然漏；只靠一个总开关又会把备份、诊断、幂等这些必须看全量的场景一起误伤。
**代价**：豁免清单要维护，且新增合理的全量查询时必须同步登记——这是有意的摩擦。

错误码约定：不存在 → `NOT_FOUND`；存在但在回收站 → `CONFLICT`（文案含「请先恢复」）。**不把回收站状态翻译成 `NOT_FOUND`**，否则前端按「数据已不存在」刷新列表，会把提示抹掉。

## 17. 客户删除按整批，界面不暴露批次

删除客户时，其名下可见订单一并进回收站，同一 `deleted_batch`；恢复与永久删除只按批次整体执行，不提供单条。
**理由**：客户与订单的关系是「客户有订单」，留下半条链比整体不可见更难解释；`orders.client_id` 是 `ON DELETE SET NULL`，硬删客户会制造无主孤儿，历史表又是 `ON DELETE CASCADE`，硬删订单会清空历史。
**代价**：无法只恢复「某个客户下的某一单」。目前判定为不需要。

`deleted_batch` 只是内部原子性依据，界面不出现 UUID。

## 18. 备份不裁剪，摘要区分总数与回收站

完整备份包含回收站数据（订单、客户、历史事件、附件关联），备份格式仍是 v1、manifest 结构不变、SHA-256 校验规则不变。
`DataSummary` 的 `orders` / `clients` 是**含回收站的总数**，另加 `trashedOrders` / `trashedClients` 表示其中回收站部分；界面展示时必须区分「全部数据」与「正常业务数据」。
**理由**：备份摘要回答的是「这个包里有什么」，不是「用户此刻能看到什么」。把回收站从总数里扣掉，会让用户在恢复后困惑「为什么少了几单」。

## 19. 财务：计划与流水分开，派生值不落库

`payment_schedules` 只描述「应收」，`payment_records` 只描述「实际到账」，退款是独立的 `refund_records`。
净到账、计划已收/未收/逾期、订单已收/待收/超额全部**现算**，表里没有 `paid_status` / `remaining_cents` / `net_cents` 这类字段。
`orders.amount_cents` 仍是订单总额，不出现第二套总额。

**理由**：一笔计划可由多笔到账分摊，落库状态一定会在某条写入路径上与流水脱节；派生值只有一个真相（流水），算出来比存下来可靠。
**代价**：读侧每次都要聚合，统计与列表要靠索引和批量查询控制成本。

> 依据类型：设计规则（[ARCHITECTURE](../architecture/ARCHITECTURE.md) 财务段、FIN-01～07 实现）。没有单独的「产品确认记录」，按当前实现记录，不作为产品裁定引用。

## 20. 费率可空，空不等于 0

`fee_rate_bp = NULL` 表示未配置或未知，`0` 表示用户明确填了 0%。`payment_records.fee_cents` 没有默认值，必须显式写入。

**理由**：把「没算过」记成「零手续费」会让净到账虚高，而且事后无法区分。
**代价**：界面必须能表达「未配置」，不能只显示 `0%`。

> 依据类型：设计规则（同上）。

## 21. 财务记录靠快照，不靠外键追溯

`platform_name`、`fee_rate_bp`、`fee_cents` 存当时的值；删平台把 `platform_id` 置空、删计划把 `schedule_id` 置空，都不删除真实流水。平台用 `archived` 标记停用，不物理删除。
**理由**：历史收款必须反映当时的手续费，而不是今天的费率；平台改名或删除不能改写已发生的钱。
**代价**：平台列表与流水列表可能显示不同名称，这是预期行为。

> 依据类型：设计规则（FIN-02 / FIN-03 实现）。「平台归档而不删除」有代码与测试证据，未找到单独的产品裁定记录。

## 22. 财务进备份，但补历史不补业务数据

四张财务表随 `database.sqlite` 快照一起备份，`FORMAT_VERSION` 仍为 1、manifest 结构不变；摘要只加四项**计数**（含已归档平台与已作废流水），不含金额与客户信息。
恢复旧包时只允许回填**平台配置**（包内没有平台表时），付款计划、收款、退款永不回填；迁移前后行数变化即拒绝。

**理由**：回填业务流水等于伪造历史；平台配置是基础资料，缺失时用本机配置比让用户重建更合理。
**代价**：旧包恢复后财务区是空的，界面必须显示「未记录收款信息」而不是「未收款」。

> 依据类型：已冻结契约（[FIN-07](../architecture/FIN-07-BACKUP-CONTRACT.md)，v0.1.2 财务工作包 7/7）。

## 23. 订单置顶是展示优先级，终态订单沉底

- `orders.pinned_at` 只影响展示：不改 `status`、不改 `queue_position`、不动 `revision`；是否生效统一由 `PIN_EFFECTIVE_SQL`（置过顶 + 进行中 + 未归档）判定，并在生命周期各路径清理。
- **已完成 / 已取消的订单不进入待排产队列**：任何排序模式下都排在活动订单之后，再按置顶分组与排序键排。手动模式下尤其如此——结束订单的 `queue_position` 可能是 0，只按位置排会把它们顶到最前。
- 排序模式有四种：手动队列 / 交付日期 / 创建时间 / 委托金额。**只有手动模式允许拖拽与上下移**；其它三种是临时视图，不写回 `queue_position`。

**理由**：置顶与排序都是「怎么看」，不是「这单是什么状态」；把展示优先级写成状态字段，会在归档、完成、取消时留下一堆需要清理的残留。
**代价**：同一份数据在不同排序下顺序不同，导出的 CSV 需要说明用的是哪种顺序。

> 依据类型：**产品裁定**（0.1.2 工作包 04 规格）+ `41a41b4` 缺陷修复（产品负责人报告「已完成/已取消订单在手动队列里乱跑」）。

## 24. 客户参考图独立归属，不与订单附件混表

客户参考图用独立的 `client_attachments` 表（v14），归属客户；`attachments` 仍是订单附件。文件共用同一棵受管目录树（`attachments/originals/clients/<客户ID>/`），但**归属不合并**，也不给 `attachments` 加 `client_id`。

**理由**：两种附件的生命周期不同——订单删除不应带走客户图，客户永久删除必须清理其全部参考图。混表会让「按订单查附件」与「按客户查附件」两套语义挤在同一主键空间里。
**代价**：多一张表、多一组命令与封面查询，但没有新增文件树、备份与校验路径。

> 依据类型：**产品裁定**（0.1.2 工作包 03：「不要为了复用组件而把客户附件和订单附件的归属关系混在一起」）。

## 25. 新建订单：类型可预设可自由输入，标题可自动生成

七种高频类型（插画、组合页、服设、设定卡、表情包、头像、摸鱼）以预设形式提供，仍允许自由输入；标题可按「客户名称 · 类型」生成，生成后仍可手改；编辑订单时可以改类型。

**理由**：预设降低高频输入的摩擦，但不该限制表达能力；标题是给人看的，自动生成只是起点。
**代价**：类型不是枚举，统计时按字符串归档，历史值可能不统一。

> 依据类型：**产品裁定**（0.1.2 工作包 01）。

## 26. 看板是扁平总览，不按阶段分列

看板按「一个流程模板 + 阶段筛选」展示订单，默认「全部流程」；不提供多模板并排或按阶段分列。阶段分列是早期方案，`d6c6861` 起改为扁平总览。

**理由**：阶段列会把「进度」和「排序」两套维度搅在一起，实际操作时要跨列找单；扁平列表配合筛选更快。
**代价**：不能一眼看到「各阶段各有几张」，需要靠筛选或统计页。

> 依据类型：**已实施的方案变更**（`d6c6861`），并在 0.1.2 交付中确认；0.1.2 只调整默认筛选与排序，不再改结构。

## 27. 统计页不做吸顶页头

统计页的页头（标题、业务/财务切换、日期范围、导出）回到普通文档流，不做 `position: sticky`、不做滚动收紧态、不加背板与阴影。切视图时回到顶部。

**理由**：产品负责人实际使用后判定吸顶干扰阅读，收益不抵遮挡。
**代价**：长列表滚动时看不到范围与导出，需要滚回顶部。

> 依据类型：**产品裁定**（实现后否决，撤回发生在 `82229bb` 之前）。页面级共用页头与统计口径不受影响。

## 28. 登录自启动以系统状态为唯一真源

设置页的「登录时自动启动」不落数据库：读取时直接查 macOS LaunchAgent / Windows Run 键；只有 plist 指向当前可执行文件才算已启用；写失败显示错误，不显示成功。

**理由**：系统启动项可以被用户或其它工具改动，缓存一份「应用以为的状态」必然与系统不一致。
**代价**：每次进设置页都要读系统，路径变化后需要重新开启。

> 依据类型：设计规则（`infra/autostart.rs` + 5 例测试）；未找到单独的产品裁定记录。

## 已否决的能力清单

以下能力在 v0.1.0 明确不做，不要在后续版本里默认它们存在：云同步、多设备同步、多用户权限、客户自助页面、在线支付、自动定时备份、备份加密、旧代际自动清理入口、阶段级图片、多订单共享同一张图片。

另外三种**被否决的实现方案**（不是「暂不做」，而是评估后不采用）：客户参考图混入 `attachments` 表（归属会混）、看板按阶段分列（维度搅在一起）、统计页吸顶页头（已实现后撤回）。理由见 §24、§26、§27。

v0.1.1 起，「永久删除与回收站」不再是「不做」项：软删除数据层（§15–§17）与回收站界面均已完成（DEV-0.1.1-03，`5a958f2`）。回收站入口位于「设置 → 数据维护 → 回收站」；订单与客户详情页提供移入回收站操作。回收站内可单独恢复独立订单、整批恢复客户组，并支持永久删除与清空。
