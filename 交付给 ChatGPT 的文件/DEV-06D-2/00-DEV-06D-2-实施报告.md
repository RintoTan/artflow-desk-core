## 4. 关键实现架构

```
DashboardPage
└─ <ProjectTimeline />            ← 只读，自己取 status() + listOrders()
   ├─ splitOrders(orders, showTerminal)        纯函数：过滤 + 排序 + 未排期拆分
   ├─ timelineWindow(scale, anchor)            纯函数：窗口（月/年按自然单位对齐）
   ├─ buildTicks(win, scale, today)            纯函数：双层刻度 + 竖线边界
   ├─ rowGeometry(order, win, today, tz, scale) 纯函数：复用 barModel → 像素
   └─ 渲染：左信息列 + 右滚动轨道（同一个 canvas）
```

- **坐标唯一来源**：`dayToX(day) = (day − win.from) × pxPerDay`。表头刻度、竖线、条、标记、今天线全部由它推出；组件里没有任何第二套换算。
- **表头与轨道同容器**：`.timeline-scroll` 同时包含 axis 与 rows，横向滚动天然同步，不需要 JS 同步 `scrollLeft`。
- **左列固定**：`.timeline-frame` 是 `grid-template-columns: var(--timeline-info-w) minmax(0,1fr)`，只有右列 `overflow-x:auto`。
- **行高共享**：`--timeline-row-h` 同时作用于 `.timeline-info` 与 `.timeline-row`，实测逐行 y 差 **0px**。

### 4.1 日期算法复用

直接 import 自 `src/lib/scheduleBar.ts`：`parseDayKey`、`daysFromCivil`、`civilFromDays`、`localDayIndex`、`barModel`、`formatDayKey`、`shortDate`。

`rowGeometry` 的做法是：**调用 `barModel` 拿到区间/标记/越界/反向区间/风险色**，只把百分比换成像素，并补上"最后一天"的宽度（设计规定区间含首尾两天）。没有复制第二套日期解析、时区换算或单条排期判断。

月份天数没有新增月份表：由 `daysFromCivil(y, m+1, 1) − daysFromCivil(y, m, 1)` 推出，闰年自动正确。

### 4.2 周起始

唯一常量 `WEEK_START_OFFSET = 0`（周一）。`weekdayIndex()`、周窗口对齐、周刻度全部读它；改周日起算只需要改这一个值，没有散落在别处。

## 5. 真实数据接入

- 数据源：`api.status()` → `workingTimezone`；`api.listOrders()` → `OrderView[]`。
- **接口返回范围已核实**：`list_orders` → `domain::orders::list()` 的 SQL 是 `SELECT id FROM orders ORDER BY …`，**没有任何 status 过滤或分页**，所以活动/已完成/已取消都会返回，终态开关不需要新接口，也不需要改后端。
- 今天：`localDayIndex(nowIso, workingTimezone)`，不使用浏览器本地时区，也不用 `new Date("YYYY-MM-DD")`。
- 逾期：只读 `order.deadlineState`，前端没有重算。

## 6. 刷新机制

| 触发 | 行为 |
|---|---|
| 进入工作台 | 首次读取，失败进入错误态 |
| 窗口重新获得焦点 | 重新读取；失败只提示，保留旧数据 |
| 「刷新」按钮 | 同上 |
| 切尺度 / 上下段 / 今天 | **不请求**，只重算几何 |

并发：每次读取自增 `requestRef`，回调里比对序号，旧响应直接丢弃；卸载后 `alive` 语义由序号 + React 卸载共同保证（组件卸载后 setState 被忽略，且不会写入 ref 序号）。

## 7. 布局实现与实测

| 场景 | 时间线框 | 信息列 | 轨道可视宽 | 行高 | 画布（月） |
|---|---:|---:|---:|---:|---:|
| 视口 900px | 547 | **177** | **361** | **52** | 2370 |
| 视口 1400px | 1039 | **299** | **739** | **56** | 2370 |
| 视口 1680px | 1319 | **299** | **1019** | **56** | 2370 |
| 容器 900px（视口 1400） | 858 | **235** | **618** | **56** | 2370 |

与原型参考值的差异（都在允许误差内，但如实记录）：

- 信息列：原型 178/300/300/235 → 实测 177/299/299/235（1px 来自边框取整）。
- 轨道：原型 369/747/1027/622 → 实测 361/739/1019/618。差 6–8px：原型把滚动条画成覆盖式，正式实现在 `.timeline-scroll` 上有经典滚动条占位（`offsetHeight − clientHeight = 15`），可视宽因此少一截。**这是平台差异，不是布局错误**；WKWebView overlay 下会更接近原型。
- `@container workspace` 只影响后代：变量写在 `.timeline-frame` 上，不写 `:root`，也不对容器自身生效。

图例：900px 下五条文字（按排期/三日内/今天到期/已逾期/已结束）全部保留，只把字号收到 10.5px、色块收到 12×7。

## 8. 滚动条策略（SCROLLBAR-01）

- **没有给时间线写任何滚动条样式**：`.timeline-scroll` 只有 `overflow-x:auto`，没有任何 `scrollbar-width` / `scrollbar-color` / `::-webkit-scrollbar`。
- 原因：仓库里没有可靠的平台标识（无 `plugin-os`，也没有既有 UA 嗅探）。按规范"未知平台保持原生、只在能确认 Windows 时定制"，本轮选择**两平台都用原生**，不新增平台识别逻辑。
- 因此 Windows 的 `thin` + `color` 方案**本轮未落地**，登记为后续项；也没有承诺任何像素宽度。
- 全站其它滚动区域未改动。

## 9. 与原型之间的差异

| 项 | 原型 | 正式实现 | 原因 |
|---|---|---|---|
| 颜色 | 部分硬编码 `#f0c3ba` 等 | 全部走主题令牌（`--danger-soft`/`--warn-soft`/`--chip-today-bg`…） | 深色主题需要跟随；`styles.theme.test.ts` 也会拦未定义令牌 |
| 轨道宽度 | 覆盖式滚动条（不占位） | 经典滚动条占 15px | 引擎默认行为，不为此写自定义滚动条 |
| 「仅开始/仅交付」标签 | 固定 12px 处 | 跟随标记位置；窗口外提示钉在可视左缘 | 画布比视口宽，钉死会滚出视野 |
| 清空态文案 | "没有任何订单填了计划日期" | 同文案，另加"补上后自动进入" | 与既有语气一致 |
| 刷新入口 | 原型无 | 新增「刷新」按钮 | 规范要求"用户主动刷新" |

其余（窗口规则、像素/天、最小宽、状态色、终态中性、未排期语义、45% 定位）与规格一致。
