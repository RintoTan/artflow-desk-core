## 一、自适应失败的实际根因

不是「差一点没调好」，是六处结构性错误叠在一起：

### 1. 行高从来没有真正的下限之外的上限逻辑

上一轮的 `monthGridMetrics` 里写着：

```ts
const base = NUM_ROW_H + MORE_ROW_H + lanes * LANE_MIN_H;   // 32+20+66 = 118
const target = available > 0 ? Math.floor(available / MONTH_ROWS) : base;
return metricsFor(..., Math.max(base, Math.min(ROW_MAX_H, target)));
```

`Math.max(base, …)` 就是那个 **118px 硬下限**：只要可用高度低于 708px（6×118），行高永远停在 118。
所以窗口从 1400×900 缩到 900×600，网格一格都没变小，只是把下面的行挤出了视口 → 出现纵向滚动条。

### 2. 高度链是断的，靠一个魔法数字撑着

```
.main { overflow-y: auto }                       /* 整页滚 */
.cal-main { max-height: calc(100dvh - 196px) }   /* 写死"页面还剩多少" */
```

`196px` 是按某一个窗口尺寸量出来的常量。窗口一矮，`.cal-main` 申请的高度和真实剩余空间对不上：
要么页面被撑出滚动条，要么日历被压掉一截。中间几层（`.main-inner` / `.cal-page` / `.cal-body`）都没有
`min-height: 0`，flex 子项会被内容顶开，`.cal-main` 的 `max-height` 根本约束不住。

### 3. `.cal-grid { min-width: 620px }`

七列本来就是 `minmax(0, 1fr)`，真正导致窄窗横向溢出、右侧日期被裁切的就是这条 `min-width`。

### 4. 首次定位用的是"占位行高"

定位逻辑（滚动到今天）跑在量到可视高度**之前**：此时 `viewportH = 0`，行高按占位值 118 算，
`scrollTop` 按 118 换算；下一帧行高变成真实值（比如 53），同一个 `scrollTop` 指向的行完全变了。
实测直接从 2026-11 漂到 2027-07。

### 5. 连续缩放用"像素比例"补偿，会累积漂移

`scrollTop = (scrollTop + clientH/2) / oldRowH * newRowH - clientH/2`，
每一步都同时合并了 `clientH` 的变化，来回拖六次就偏了几个月。

### 6. `.cal-chip-action`（改期小按钮）占布局宽度

窄格里它以 `opacity: 0` 隐形却仍然吃宽度，把订单标题挤成一个圆点 —— 表现像"订单条没有内容"。

## 二、修改文件与关键改动

| 文件 | 改动 |
| --- | --- |
| `src/lib/calendar.ts` | 重写 `GridMetrics`（新增 `lanes/chipH/fontPx`）；`monthGridMetrics(availableH, weeks)` **按当月实际周数（4/5/6）均分可用高度**，`rowH = floor(可用高/周数) - 1`（扣 1px 分隔线），下限只留 44px；行矮时先降轨道数 3→2→1，而不是把每格压成缝；新增 `weeksInMonth()`；`weekGridMetrics()` 固定 6 轨不参与自适应 |
| `src/components/CalendarGrid.tsx` | 轨道数、行高、条高、字号全部来自 `metrics`；`.cal-grid` 上挂 `--cal-num-h / --cal-more-h / --cal-chip-h / --cal-chip-font` 四个变量统一驱动 |
| `src/pages/CalendarPage.tsx` | 行高改为 `monthGridMetrics(viewportH, weeksInMonth(monthAnchor))`；**未量到 `viewportH` 之前不定位今天**；缩放补偿改为「视口中心落在第几行」的行序号换算（不累积漂移）；同时跟踪 `clientH` 变化 |
| `src/App.tsx` | 日历路由给 `<main>` / `.main-inner` 加 `main-fixed` / `main-inner-fixed` |
| `src/styles.css` | 新增 UI-06 自适应段：整页不滚（`.main-fixed` 的 flex 链 + 每层 `min-height: 0`）、去掉 `.cal-main` 的 `calc(100dvh-196px)`、`.cal-grid { min-width: 0 }`、数字/条/字号全部走变量、窄窗工具栏不折行、改期小按钮改绝对定位 |
| `src/lib/calendar.test.ts` | 网格度量测试重写（整月高度不超可视高、4 周月比 6 周月行更高、轨道随行高降级、极端矮窗口不低于下限）+ `weeksInMonth` 三例 |
| `scripts/calendar-fit-probe.mjs` | 新增：五档尺寸的布局取证（溢出/滚动条/整月可见/等宽等高/数字位置/缩放单调性） |

数据库、迁移、后端日期写入、编号规则、生命周期语义均未改动。

## 五、未解决问题与必须说明的风险

1. **UI-06 交互回归脚本（`calendar-ui06-probe.mjs`）在本轮布局改动后出现 FAIL，尚未修好。**
   该脚本的多处断言写死了旧几何（浮层只折叠 1 笔、`+N` 一定在视口内、跨月边界按 118px 行高定位），
   新布局下行高变成 46~118、轨道 3→1，这些前提不再成立。**目前无法确认这些 FAIL 全部是脚本假设问题**
   —— 其中「点击非当月日期」「跨月边界定月」两项有可能是真实回归。
   本轮没有时间逐条甄别，按"未验证"处理，不计入通过。
2. 1400×1000 的实机截图里，满行 `+N` 贴着周分隔线，视觉上略挤（功能正常，未调整间距）。
3. 900×600 时订单条只剩 1 条轨道，更多订单折叠进 `+N`；这是刻意的取舍（保可读性），但会让该尺寸下的信息密度明显下降。
4. 事件来源仍是合成 AppKit 事件（走真实命中测试），不是物理鼠标；原生"手感"仍需人工确认一次。
5. 历史遗留不变：`ISSUE-02` 的「10-16」一半、`DEV-06D-1` 仍 `OPEN / PARTIALLY ACCEPTED`、`DOCK-01` OPEN/P1。
