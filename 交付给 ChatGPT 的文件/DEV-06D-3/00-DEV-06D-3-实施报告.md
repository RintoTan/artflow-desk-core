## 3. 改期历史数据结构

`order_events` 中 `kind='rescheduled'` 的一行即一次改期：

| 列 | 含义 |
|---|---|
| `old_start_date` / `old_delivery_date` | 改动前计划日期（NULL = 该端为空） |
| `new_start_date` / `new_delivery_date` | 改动后计划日期 |
| `reason` | 选填原因（≤200 字符，空白归一为 NULL） |
| `change_source` | `calendar` / `order_details`（CHECK 约束，未知值被拒） |
| `occurred_at` | 修改时间 |
| `from_status` / `to_status` | 恒为 NULL（改期不是状态变更） |

`note` 列不参与改期，避免与制作备注混淆。

## 4. 核心业务流程

```text
拖放/键盘/浮层
  → 纯函数 dropPlan(order, targetDay, mode, field?)   // 只算，不写
  → 若 ok：RescheduleDialog（展示前后 + 原因 + 影响说明）
  → 确认 → api.updateOrderDetails(rescheduleInput(...))   // 整单回填
      后端：BEGIN IMMEDIATE
        → 读当前行（含 status / 旧日期 / revision）
        → 校验标题、金额、日期格式、区间（delivery >= start）
        → 内容完全一致 → 直接返回，不 bump revision、不写事件
        → 日期有变且 status != active → INVALID（终态守卫）
        → revision 不匹配 → CONFLICT
        → UPDATE 8 个资料列 + revision + updated_at（WHERE revision=?）
        → 日期有变 → INSERT rescheduled 事件（同事务）
        → 返回最新 OrderView
      COMMIT（任一步失败整笔回滚）
  → 前端重载列表；冲突时对话框保留并显示后端原文
```

终端隔离：

- 拖放阶段 `update_order_details` 调用数 **0**（浏览器实测）。
- 取消对话 → 关闭、0 次写入、无历史。
- 同日/未变化 → 后端短路，不写事件。

## 5. 产品规格逐项对应

| 规格 | 结论 | 证据 |
|---|---|---|
| §1 只读写计划日期，不碰阶段/开工/完成/队列 | 达成 | `update_details` UPDATE 列清单不含 status/work_state/queue_position/started_at/completed_at |
| §2 独立侧栏入口 + hash 路由 + Arctic 令牌 | 达成 | NAV 第 2 项、`#/calendar`、`.cal-*` 仅用令牌（`styles.theme.test` 通过） |
| §3.1 月视图 6×7=42、周一起始、邻月弱化、高度稳定 | 达成 | 探针 `weeks=6 / cells=42`，六行高度 105/105/105/105/105/104；`weekStartOf` 每周一 |
| §3.2 周视图 7 列、横向日期网格、无小时刻度 | 达成 | `1×7`，无时间轴元素 |
| §3.3 切视图保留浏览日期，不前跳今天 | 达成 | 单测：11 月 → 下一段（12 月）→ 切周，标题仍为 `2026-12-14 ~ 2026-12-20` |
| §3.4 复用日期原语 + `workingTimezone` | 达成 | `calendar.ts` 只 import `scheduleBar`/`timeline` 原语；今天 = `localDayIndex(now, tz)` |
| §4 双日期/仅开始/仅交付/同日/未排期 | 达成 | 探针确认四种 `data-kind` 同时出现；未排期只进左池 |
| §5 月 3 / 周 6 轨道、跨周重排、+N 按当天去重 | 达成 | 单测 8 例；探针同日 4 单 → `+1` |
| §5.1 活动优先 → 最早交付 → 编号；终态不挤活动 | 达成 | `compareForLanes`；单测「活动占轨、终态进折叠」 |
| §5.2/5.3 +N 浮层 + 每单改期入口 | 达成 | 探针打开浮层并找到「改期」按钮 |
| §6 风险色读 `deadlineState`，终态不着色 | 达成 | `tone()` 只读字段；终态加 `is-terminal` 中性样式 |
| §7 未排期池按创建时间→编号；拖入必须选端 | 达成 | `compareUnscheduled`；对话框「写入计划开始/交付」单选，另一端保持为空 |
| §7.1 不支持拖回池；详情清空后回池 | 达成 | 池只读；清空经详情保存（写 rescheduled） |
| §8 显示已结束开关 + 终态不可拖 + 历史分区 | 达成 | 单测：默认 1 条 chip；开启后终态 `data-mode=none`、出现「已结束且未排期」 |
| §9 拖动→预览→确认→写入；取消零写入 | 达成 | 探针：`writes=0`（拖动中）、取消后仍 `0` |
| §9.1–9.7 六种语义 + 跨周延续段 + 非法日期 | 达成 | `dropPlan` 六种 mode；`clippedLeft/Right` 标注延续段；开始>交付被拦截（对话框内提示且按钮禁用） |

## 9. 已知问题与风险

| # | 问题 | 影响 | 建议 |
|---|---|---|---|
| R1 | `update_order_details` 整单覆盖，日历必须回填全部字段 | 漏填会清空金额/客户/来源/备注 | 已有 `rescheduleInput()` 单点生成 + 后端测试「字段保留」；后续新增入口必须复用它 |
| R2 | 终态守卫会拒绝**任何**日期变化，包括"清空日期" | 终态订单无法在详情里清空计划日期 | 符合 D6 裁定；若产品要允许，需单独放宽 |
| R3 | 迁移 v6 重建表 | 大库（数十万事件）会有一次性停顿 | 当前单画师数据量可忽略；实测 3 条事件 < 10ms |
| R4 | 拖放在 WKWebView 下的指针行为未实测 | 可能影响拖动流畅度 | 与队列拖拽同一套 Pointer Events（该功能已在实机使用），风险低但未验收 |
| R5 | 月视图格子内标题只能显示 6–8 字 | 长标题靠 `title` 与详情页 | 规格允许；如需更多信息可后续加悬停卡 |
| R6 | `vitest run` 曾出现一次 `OrdersPage.stageOps` 抖动（单独跑与重跑两次均 518 全绿） | 无功能影响 | 已记录，未改测试；若复发再定位 |
| R7 | 日历页未加"未保存草稿"守卫 | 日历本身无草稿 | 若未来在日历里加内联编辑需补 |
