# 01 · 附件导入实施报告

## 一、审计结论：拖拽导入已存在，本轮不重复实现

| 检查项 | 实际实现 |
| --- | --- |
| 导入入口 | `AttachmentPanel`：「选择图片」走 `@tauri-apps/plugin-dialog` 的 `open({multiple:true})` |
| 拖拽导入 | **已实现**：`getCurrentWebview().onDragDropEvent()` 监听 `enter/over/leave/drop` |
| 命中判定 | `src/lib/attachmentDrop.ts::decideDrop()` —— 物理像素 ÷ devicePixelRatio 换成 CSS 像素后与面板 rect 比较 |
| 多文件 | 支持（`paths` 数组，逐项 import） |
| 重复拖拽 | `dedupeMs`（默认 800ms）内二次 drop 被忽略 |
| 换单守卫 | 拖拽开始时记下 orderId，drop 时与当前 orderId 比对，不一致则不导入并提示 |
| 格式/大小限制 | 前端按扩展名预过滤（`partitionImagePaths`），后端做魔数校验与尺寸上限 |
| 临时文件 | 导入走 `attachment_jobs`：先写 job → staging → 原子 rename → 写元数据 → job=done |
| 一致性 | 写元数据失败时删除已复制的原图/缩略图，job 置 failed（不留孤儿） |

结论：TASK 02 的功能点在上一阶段已经落地，本轮**没有改导入逻辑**，只核对其口径与安全边界。

## 二、为什么拖拽与排序不冲突

- Tauri 的窗口拖放（`dragDropEnabled`）与 HTML5 DnD 是两套机制。`tauri-utils 2.10.2` 中 `drag_drop_enabled` 的默认值为 `true`（`config.rs:2408`），本项目未显式关闭，因此：
  - 系统文件拖入 → 由 webview 层投递 `DragDropEvent`，HTML5 `dragover/drop` 被抑制；
  - 订单列表排序用的是 **pointer 事件**（`pointerdown/pointermove/pointerup` + `setPointerCapture`），不经过 HTML5 DnD，因此不受影响。
- 项目未在配置里写 `dragDropEnabled`，等于沿用 Tauri 默认值；这是**核实后的结论**，不是假设。
- 拖放监听只挂在 `AttachmentPanel` 一个组件上（`getCurrentWebview()` 全局事件 + 矩形命中），落到面板外直接忽略，不会全站拦截。

## 五、批量失败处理（TASK 03 核对结果）

`attachments::import()` 对每个文件独立返回 `ImportOutcome { sourceName, ok, attachment, error }`：

| 场景 | 实际行为 |
| --- | --- |
| 全部成功 | 提示「已导入 N 张图片」 |
| 部分失败 | 提示「成功 X 张，失败 Y 张」+ 逐个「文件名：原因」 |
| 全部失败 | 同上，X=0；已存在附件不受影响 |
| 扩展名不支持 | 前端预过滤，直接给出「文件：原因」，不进后端 |
| 读文件失败 / 魔数不符 | 后端返回该项失败，其它项继续 |
| 写元数据失败 | 删除已落盘的原图与缩略图，job=failed |
| 用户取消选择器 | `picked` 为 null 直接 return，零副作用 |
| 导入中崩溃 | 启动时 `recover()`：已写元数据的补 job=done；无元数据的文件移到 `quarantine/` 并 job=failed |

无静默失败路径：每个失败项都带 `error` 文案，前端必须展示。
