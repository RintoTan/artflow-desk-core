## 一、审计结论

| 对象 | 现状 | 本轮处理 |
| --- | --- | --- |
| `attachments/quarantine/` | 只增不减，无自动清理 | **新增**只读盘点 + 手动清理（默认不删） |
| `attachment_jobs` | 永久保留，无清理机制；状态只有 `pending/done/failed` | **新增**盘点 + 按天数手动清理历史记录 |

| 孤儿文件 | 导入失败会删；崩溃遗留会被移进 quarantine | 未改动 |

`attachment_jobs.state` 的 CHECK 只允许 `('pending','done','failed')` —— **没有 running 状态**。维护面板的 `running` 计数恒为 0，保留该字段仅为将来扩展时不用改前端。

## 二、quarantine 是什么

崩溃恢复时，如果导入/修复任务留下了一个「没有元数据指向它」的文件，`move_to_quarantine()` 会把它改名移进 `attachments/quarantine/`（前缀 8 位 uuid，避免重名）。它的用途是**人工比对**：用户可能想把这张图手工补回去。

所以它不是垃圾箱，清理策略必须是「人看着删」而不是「按时间删」。

## 三、本轮实现（`src-tauri/src/domain/maintenance.rs`）

### quarantine 盘点 `maintenance_quarantine`

返回：目录绝对路径、文件清单（名称 / 字节 / 修改时间 / **是否仍被引用**）、总占用、被引用数、可清理数与可清理字节。

「被引用」= 出现在 `attachments.rel_path`、`attachments.thumb_rel_path`、`attachment_jobs.rel_path`、`attachment_jobs.temp_rel_path` 任一列里。

### quarantine 清理 `maintenance_quarantine_clear(names)`

- 只接受「quarantine 目录下的单个文件名」：含 `/`、`\`、`..`、以 `.` 开头的名字一律跳过并计数 `skippedUnsafe`；
- 仍被引用的 → 跳过并计数 `skippedReferenced`；
- 符号链接 / 非普通文件 → 跳过；
- 逐个删除，失败逐个记入 `errors`，不因个别失败中断整体；
- 返回 `removed / bytesFreed / skippedReferenced / skippedUnsafe / errors`。

因为被删文件本来就没有数据库行指向它，删除**不需要事务**，也不存在「事务未提交就删文件」的问题。

### 作业记录盘点 `maintenance_jobs(pruneDays)`

返回状态分布（pending / done / failed / total）、最早一条时间、按当前天数阈值的可清理条数。

### 作业记录清理 `maintenance_jobs_prune({ olderThanDays, dryRun })`

- 只删 `state IN ('done','failed')` 且 `updated_at < cutoff` 的行；
- `pending` **永不参与**：它是崩溃恢复的唯一线索；
- `dryRun: true` 只统计不删（前端二次确认前的预览用）；
- 天数被 `clamp(1, 3650)`，不接受 0 或负数；
- 只删记录，不动任何文件。

## 四、前端（`src/components/AttachmentMaintenancePanel.tsx`）

设置页新增「附件维护」：

- 隔离文件：占用 / 仍被引用 / 可清理三个数字 + 文件清单（被引用的排在前面并标注「仍被引用」）；
- 按钮「清理可清理的 N 个文件…」→ 二次确认框列出将删名单 + 「删除后不可恢复」→ 确认后提交；
- 作业记录：总记录 / 状态分布 / 最早一条；「清理早于 [30/90/180/365] 天」+「清理历史记录…」→ 二次确认框显示匹配条数与保留说明；
- 两处都写明「没有自动清理」「待处理记录永不清理」。

默认值：作业清理阈值 90 天（只是下拉默认项，用户不点按钮就什么都不会发生）。

## 六、安全边界（逐条对照需求）

| 要求 | 实现 |
| --- | --- |
| 不自动清空 quarantine | ✅ 无定时器，只在点击后执行 |
| 不按文件年龄自动删 | ✅ 完全不看年龄 |
| 不删仍被引用的文件 | ✅ 四列引用检查，命中即跳过并回报 |
| 不误删正常附件 | ✅ 只接受 quarantine 目录内的单文件名 |
| 清理失败保留诊断 | ✅ `errors` 逐条返回，文件保留 |
| 清理前明确确认 | ✅ 二次确认框列出名单/条数 |
| 不删 pending/running 任务 | ✅ SQL 只匹配 done/failed |
| 不无限重试 | ✅ 单次执行，无重试循环 |
| 数据库提交与文件删除分离 | ✅ 被删文件无 DB 行；作业清理只删行不动文件 |
| 不误删仍被其他记录引用的物理文件 | ✅ 同上（引用检查） |

## 八、attachment_jobs 清理规则：产品决策待确认（本轮不改）

现状核对（逐条对代码）：

| 检查点 | 实际实现 | 结论 |
| --- | --- | --- |
| 默认天数是否 90 | `AttachmentMaintenancePanel` 的 `useState(90)`，下拉默认选中 90 天 | 是 |
| 周期是否正确传给 Rust | `maintenanceJobsPrune({ olderThanDays: pruneDays, dryRun: false })` → `PruneInput` | 是 |
| SQL 是否严格排除 pending | `WHERE state IN ('done','failed') AND updated_at < ?1` | 是 |
| dryRun 是否零写入 | `if input.dry_run { 0 } else { DELETE … }`；测试断言 `removed == 0` 且行数不变 | 是 |
| 是否有二次确认 | 面板内 `role="alertdialog"`，列出匹配条数 + 保留说明，确认后才调命令 | 是 |
| 是否只删作业记录 | 只 `DELETE FROM attachment_jobs`，不碰任何文件 | 是 |
| 失败是否保留诊断 | 命令返回 `Result`，失败整体报错不改数据；删除是单条 SQL，无部分成功 | 是 |

**这些行为只是「能力」，不是「政策」。** 90 天只是下拉框的默认选中项，用户不点按钮就什么都不会发生；代码里没有定时器、没有启动时自动清理。

| 周期 | 影响范围（以 QA 现有 7 条记录为例） | 风险 |
| --- | --- | --- |
| 30 天 | 可能清掉约 1 个月内已完成的导入记录 | 早期排障线索变少 |
| 90 天（当前默认） | 保留最近一季度，覆盖绝大多数「这张图什么时候导的」追问 | 平衡 |
| 180 天 | 几乎只清去年遗留 | 记录表缓慢增长 |
| 365 天 | 基本等同不清理 | 表增长最慢消失 |

建议（待确认，本轮不动）：

1. **保留期建议 90 天**，但把它明确写进产品文案，而不是靠默认值暗示；
2. 增加「只保留最近 N 条」的上限保护（例如 5000 条），防止长期使用后表无限增长——这属于新策略，需单独确认；
3. `pending` 记录实际是崩溃恢复的唯一线索，但如果长期存在（比如某次恢复永远失败），建议在维护面板里单独列出来让用户看到，而不是静默保留。

在上述任一条被确认之前，**当前实现与 QA 数据保持不变**，本轮没有执行任何真实清理。
