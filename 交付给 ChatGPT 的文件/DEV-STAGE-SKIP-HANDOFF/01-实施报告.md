## 二、v7 迁移设计

- 重建 `order_events`（SQLite 不支持改 CHECK），`kind` 增加 `stage_skipped`；
- 新增 `skipped_stages TEXT`（JSON 数组快照）、`skip_reason TEXT`（选填）；
- 两条 CHECK：
  - `stage_skipped` 必须有合法、非空 JSON 数组快照；
  - 其它类型不得写 `skipped_stages`；
- 按 `id` 原样搬运全部历史列（含 v6 六个改期字段、`reason`、`change_source`、`request_id`）；
- 重建三个索引：`order_events_order_idx`、`order_events_kind_idx`、`order_events_request_uniq`（部分唯一）；
- 保留 `REFERENCES orders(id) ON DELETE CASCADE`。

快照格式：`[{"stage_id":"refine","title":"细化","position":3}]` —— 名称是跳级当时的快照，之后改模板不影响历史。

## 三、领域动作

`skip_stage { order_id, target_stage_id, expected_revision, reason?, request_id? }`

单事务：幂等短路 → revision 校验 → 状态/开工校验 → 在本单 `order_stages` 内定位目标 → 校验"必须跨过 ≥1 个中间阶段" → 更新 `current_stage_id` 且 `revision+1` → 写 `stage_skipped` 事件（含快照与原因）。

拒绝：当前阶段 / 更早阶段 / 只差一级 / 不存在 / 未开工 / 已完成 / 已取消 / revision 过期；全部零写入（阶段、revision、事件数均不变）。
`queue_revision`、`status`、`started_at`、`completed_at`、`cancelled_at`、`queue_position`、`work_state` 不动。

`stage_moved_after` 纳入 `stage_skipped`：跳级后即便返工回第一阶段，撤销开工仍被拒绝（与推进语义一致）。

## 四、UI

- 阶段面板保留唯一入口「推进阶段…」，内部三区：推进 / 跳级 / 返工；
- 跳级区只列 `index ≥ current+2` 的目标，标注「将跳过：A、B」；
- 选中跳级目标后对话框标题变「跳级阶段」、按钮变「确认跳级」，并出现摘要块：
  订单编号+标题、当前→目标、被跳过列表、原因输入、「被跳过的阶段不会记为已完成」；
- 阶段列表：被跳过的阶段加 `stage-skipped`（虚线 + 名称删除线 + 「已跳过」胶囊），与「已完成」区分；
- 制作历史：新增「跳级」标签，展示 `原阶段 → 目标阶段 · 跳过 X、Y · 原因`。

「已跳过」由事件回放派生（`skippedStageIds`），不落库；返工重新进入该阶段后自动消失，历史事件保留。
